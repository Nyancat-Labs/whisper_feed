# Deep dive: security, correctness and performance

A read of the whole app — manifest, permissions, network configuration,
WebViews, intent surfaces, storage, database, dependencies and the release
build — with everything found either fixed here or written down below with the
reason it was not.

Verified at the end of the pass: **165 unit tests, 0 failures; 0 lint errors
with the report now a build gate; `assembleRelease` green, so R8 shrinking and
the keep rules still hold.**

Nothing here has been run on a device. Every item marked **device** needs a
phone before it can be called done.

---

## Fixed

### 1. Plaintext HTTP was permitted everywhere — *security*

`network_security_config.xml` carried `cleartextTrafficPermitted="true"` in
`base-config`, so every request the app makes could travel unencrypted. That
matters more here than in most apps, because of what the app does with what it
fetches: it renders article HTML in a WebView with JavaScript enabled, and it
signs in to self-hosted Google Reader servers with a **username and password**
over ClientLogin. On an http server those credentials crossed the network in
the clear, and anybody on the path could rewrite an article body before it
arrived.

Now `false`. An http-only feed fails to fetch, visibly: three failed syncs and
it appears under Broken feeds with its reason, which beats silently accepting a
page anyone on the café wifi could have written.

The same file also declared a `<domain>` of `file:///android_asset/`, which is
not a domain and matched nothing. Removed.

### 2. The full-text fetcher had no SSRF guard — *security*

`BlockPrivateNetworks` — the interceptor that refuses RFC1918, loopback,
link-local, carrier-grade NAT and IPv6 unique-local addresses — was installed
on `FeedParser`'s client only. `fullTextClient` had none, and it is the more
exposed of the two: a feed address is at least something the reader typed or
imported, but an article link is a string a publisher puts in an XML file, and
this client fetches every one of them in the background.

A hostile or merely compromised feed listing
`<link>http://192.168.1.1/admin?reboot=1</link>` would have had the phone reach
into its own network and store what came back. Now guarded, as a *network*
interceptor so it fires on every redirect hop rather than only on the address
first requested.

### 3. Images went out through an unguarded client — *security + performance*

Every `<img src>` in the feed comes out of somebody else's XML, and Coil was
using the default loader it builds for itself: no interceptor, so the same
private-network probe was available through an image tag.

Whisper now supplies its own `ImageLoader` with the interceptor, and while
there, cache limits that suit a feed: 20% of the heap for memory, a fixed
128 MB on disk. Coil's default disk budget is 2% of the free space on the data
partition — gigabytes on an empty phone, a few megabytes on a full one, which
is the wrong way round on both.

### 4. The in-app browser would open any scheme — *security*

`ComposeWebView` runs with JavaScript and DOM storage on, had no
`shouldOverrideUrlLoading`, and left `allowFileAccess`/`allowContentAccess` at
their defaults. It is also reachable from **outside the app**: `MainActivity`
is exported (as a launcher activity must be) and
`nf-navigation://androidx.navigation/webview/{url}` is a registered deep link,
so any installed app can point Whisper's browser somewhere by explicit intent.

Now: http and https only, checked before the WebView is created and again on
every navigation; file and content access off; mixed content never allowed;
Safe Browsing on. A non-web link is handed to the system instead.

### 5. Any app could open arbitrary URIs through the app — *security*

`Context.launchView` fired `ACTION_VIEW` at whatever string it was given, and
every caller passes content somebody else wrote: an `<a href>` in an article
body, a link in the browser, a URL from an OPML. Now an allowlist —
http, https, mailto, tel, sms, geo, market — so a `content://`, `file://`,
`javascript:` or `android-app://` link in a feed does nothing.

The scheme parser is deliberately not `Uri.parse`: that class is a stub in unit
tests, so a check written with it could only ever be verified on a device, and
these two checks are what stands between a feed's contents and an intent
leaving the app. `schemeOf` follows RFC 3986 and is covered by 9 tests.

### 6. Any app could bind the overlay service and read the feed — *security*

`OverlayService` is exported, which it must be — a launcher in another process
is the whole point — but it accepted a bind from anybody. An app holding no
permissions at all could bind, hand over a window token of its own, and have
Whisper render the reader's feed inside it: titles, sources, what has been
read.

It now accepts binds only from a caller whose package answers `CATEGORY_HOME`,
plus its own uid. That is exactly the set of callers with a reason to be there,
and it needs no list of package names kept up to date.

The caller is identified from the bind Uri — the LauncherClient protocol puts
the calling uid in the port and the package in the host — and the package
manager is asked whether that package really belongs to that uid before
anything else is decided.

The first version of this fix used `Binder.getCallingUid()`, which is wrong in
a way worth recording: `onBind` is dispatched on the main thread, outside the
binder transaction, and there that method returns *this* process's uid. The
check would have passed for every caller while looking like it did something.
The lint gate turned on in item 16 caught it on its first run.

**device** — worth confirming Lawnchair still connects. A launcher that binds
from a helper package with no home activity would now be refused.

### 7. A dead intent-redirection shape — *security*

`MainActivity.start()` put a caller's `Intent` into an extra named `"intent"`
and a `ResultReceiver` into one named `"callback"`. Nothing called it and
nothing read those extras — but that is the classic intent-redirection hole and
this activity is exported, so the next person to wire it up would have handed
every app on the device a way to launch arbitrary intents with Whisper's
identity. Deleted, with a note saying why.

### 8. An autoVerify deep link for a domain we do not own — *security*

The manifest claimed `http`/`https` links to `neofeed.saulhdev.com` with
`android:autoVerify="true"`. This project cannot publish an `assetlinks.json`
for someone else's domain, so verification could only fail, and Whisper offered
itself in the chooser for a website it has nothing to do with. Nothing in the
app routes on that host. Removed.

### 9. Launcher detection was broken on Android 11 and later — *bug*

The manifest had no `<queries>` block. Since Android 11 that means
`getPackageInfo("app.lawnchair")` throws NameNotFound whether or not Lawnchair
is installed, so `LauncherLink.installedLauncher` always returned null: the
launcher setup screen told **everybody** they had no supported launcher, and
`getLaunchIntentForPackage` returned null so the button to open its settings
did nothing.

Now declared, as intents rather than package names — home, view-https and
send-text — which also settles the two standing `QueryPermissionsNeeded` lint
warnings.

### 10. The in-app browser could not follow a link — *bug*

`AndroidView`'s `update` block compared the WebView's live URL against the one
the screen was opened with and called `loadUrl` whenever they differed. That is
true from the first tap on any link, and `update` runs on every recomposition —
of which the progress bar alone causes dozens. Tapping a link inside an article
snapped straight back to the article.

Now it reloads only when the *screen* is pointed at a different address.

### 11. Back in the browser closed the app — *bug*

The same screen's `BackHandler` consulted a `rememberNavController()` created
locally and attached to no graph. Its `currentBackStackEntry` is therefore
always null, so the else branch never ran and the first back press called
`activity.finish()` — closing the whole app from a page the reader had opened
to read. Back now walks the browser's history, then leaves the screen.

### 12. The browser said "Neo Feed" — *bug*

Three hardcoded fallbacks in the title and subtitle. Now the app's own name.

### 13. A modal permission nag on every launch — *bug*

A dialog opened over the home screen on every launch if "Display over other
apps" was not granted, with one button, going to system settings.

The permission is not useless — see *Known and kept* below — but it is only
needed by people attaching Whisper to a launcher, and the launcher screen
already explains it in context. Demanding it of every reader on every launch,
before they have seen the app, was the wrong place to ask.

### 14. The changelog was always light — *bug*

`PreferencesWebView` hardcoded `light.css`, so the changelog and licence pages
opened as a white sheet in the middle of a dark app. `dark.css` was shipped in
the assets all along and never referenced. Three more bugs in the same
function, all fixed:

- `shouldOverrideUrlLoading` tested the *outer* `url` rather than
  `request.url`, so every link on the page led back to the page itself.
- JavaScript was switched off on the line after `loadUrl("javascript:…")`, while
  that call was still queued — so whether the stylesheet applied at all came
  down to a race. Now `evaluateJavascript`, switched off in its callback.
- `update` called `loadUrl` on every recomposition, throwing away the scroll
  position and re-running the injection each time.

### 15. A blocking disk read per launcher message — *performance*

`OverlayView.onClientMessage` called `prefs.debugging.getValue()`. Every
preference read goes through `runBlocking` on a DataStore, so this was a disk
read on the main thread each time the launcher said anything — including the
message that arrives as the panel is being swiped open, which is the one frame
that must not stall. Read once now.

### 16. Two unused build features and a lint report nobody had to read

`dataBinding` and `viewBinding` were both on and neither used: no layout has a
`<layout>` root and nothing names a generated `*Binding` class. Each added a
code-generation pass to every build.

`lint { abortOnError = false; checkReleaseBuilds = false }` meant a lint error
changed nothing about the build and was only found by someone opening the
report on purpose — which is how an API-28 call in a minSdk-26 app, a crash on
every Android 8 phone, once sat in it unnoticed. The report is clean, so it is
a gate now.

## Known and kept

**`SYSTEM_ALERT_WINDOW`.** No line of code uses it, and the overlay panel does
not need it to draw: the launcher passes its own window token across the binder
and the panel is attached to it as an ordinary application window. It is held
for the *other* thing the system grants it — holding this permission is a
documented exemption from the background-activity-launch restrictions, and
opening an article from inside the overlay is a background activity start. The
`PendingIntent` opt-in in `Context.safeStartActivity` only lets a caller pass on
privileges it already has. Without the exemption, tapping an article in the
panel does nothing at all.

This looked at first like dead over-privilege and is not. It is now documented
in the manifest so the next reader does not have to work it out again.

**device** — if an article opens from the panel on a build with the permission
revoked, it can go.
